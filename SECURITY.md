# Security and biosecurity

## Software vulnerabilities

Do not open a public issue for a vulnerability that could put users, data, or infrastructure at immediate risk. Use the repository's private security-reporting channel and include the affected version, component, reproduction conditions, impact, and a safe minimal demonstration. Do not include real credentials, patient data, or restricted datasets.

Maintainers will first determine whether the report is reproducible and in scope. They will coordinate a correction and disclosure window proportionate to the risk. Educational examples are not a promise that third-party software is secure.

## Biological capability escalation

AIDD Commons covers dual-use methods at a level needed for responsible graduate education. Public contributions must not materially increase harmful operational capability. Escalate privately before posting when a contribution could substantially improve the design, acquisition, optimization, evasion, or deployment of a biological agent or harmful chemical, especially when it combines actionable parameters, optimization code, and validation guidance.

Ordinary discussion of safety evaluation, high-level mechanisms, public benchmark behavior, or defensive detection is not automatically restricted. The question is whether the specific contribution meaningfully lowers the practical barrier to harm.

Stewards may ask for scope reduction, delayed disclosure, expert review, access controls, or rejection. They document the public rationale at a level that does not reproduce the risky content. Safety review does not excuse unsupported censorship; decisions should name the capability change and the least restrictive adequate response.

## Data and model handling

Do not contribute protected health information, confidential research data, controlled substances procurement details, private keys, access tokens, or material whose terms prohibit redistribution. Link to lawful upstream access instructions instead. Model and dataset cards must preserve restrictions and known misuse limitations.

## Supported versions

Security corrections target the current public release and the default development branch. Older snapshots may remain available for scientific provenance but are not maintained unless a release notice says otherwise.
