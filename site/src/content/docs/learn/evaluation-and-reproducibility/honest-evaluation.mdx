## Foundations

Evaluation begins with the unit expected to generalize: molecule, scaffold,
target, protein family, assay, patient, time period, or experimental campaign.
A high score is not informative until the split, labels, leakage controls, and
comparison protocol are explicit.

## Practical workflow

Write a data contract and freeze split construction, model selection, metric,
and uncertainty reporting before model comparison. Use a cheap baseline and
audit duplicate, scaffold, target, and time overlap. [Therapeutics Data
Commons](https://tdcommons.ai/) and [OGB](https://ogb.stanford.edu/) publish
task definitions, but a project still needs to inspect the matched endpoint.

## Evaluation

Report the benchmark version, inputs, labels, splits, selection protocol,
failed runs, and uncertainty over the actual independent unit. For structures,
[PoseBusters](https://github.com/maabuu/posebusters) checks selected physical
plausibility conditions; it does not validate biological efficacy.

## Audit the evaluator as part of the instrument

The [BenchGuard paper, revision v2 dated 2026-10-02](https://arxiv.org/html/2604.24955v2), treats an execution benchmark as a coupled contract among instructions, reference programs, evaluators and environments. Its method asks an external language model to cross-check those artifacts, optionally using agent code or traces as diagnostic evidence. The audit workflow introduces no newly trained model. A finding is a candidate for expert review; the paper's reported defect counts are not defects independently reproduced in this lesson.

Version changes matter on both sides of that contract. The [ScienceAgentBench maintainer notice](https://github.com/OSU-NLP-Group/ScienceAgentBench) dated 2026-04-30 announces a `verified` dataset split and `benchmark_verified.zip` to reduce false-negative grading. That establishes a revision to name, not proof that every remaining task is correct. Preserve the instruction, input, reference, evaluator and environment versions before comparing old and revised scores.

### Constructed case: a grader measures the wrong property

This is an original handworked example, not a task from either benchmark. The instruction requests one arithmetic mean per sample, with row order irrelevant. Sample A has observations `2, 4`; sample B has `4, 6`. The reference table is `A: 3; B: 5`. A defective evaluator E0 accepts exactly two rows whose sample IDs appear in the order `A, B`, but never checks their mean values. The declared environment parses the means as numbers, so `3` and `3.0` have the same meaning.

| Submitted rows | Scientific contract | E0 |
| --- | --- | --- |
| `A: 3; B: 5` | Valid reference | Accepts |
| `B: 5.0; A: 3.0` | Valid alternative order and numeric spelling | Rejects |
| `A: 3; B: 6` | Incorrect mean for B | Accepts |

What does E0 actually measure? State a repair that accepts the valid alternative and rejects the known error. If a later instruction explicitly requires sorted rows, does the second submission still satisfy that revised contract?

<details data-worked-answer>
<summary>Worked answer</summary>

E0 measures identifier order and row count, not the requested calculation. The means are `(2 + 4) / 2 = 3` and `(4 + 6) / 2 = 5`. A repaired evaluator should require the declared columns, unique and complete sample IDs, parse numeric values, align by sample ID and check the exact means in this exercise. A real benchmark must declare the tolerance appropriate to its measurements. The repair should accept the second row of the teaching table and reject the third. Missing or duplicate IDs need their own rejection cases. If sorted output becomes an explicit requirement, the reversed submission fails that new format requirement; record the instruction and grader revision rather than silently relabelling an old agent result. A reference-program mismatch, an agent error and an environment failure require different diagnoses.

</details>

## Frontier and open questions

Out-of-distribution evaluation, dataset shift, label noise, and benchmark
leakage remain active problems. [DrugOOD](https://drugood.github.io/) makes
one family of distribution shifts explicit, not every way a deployed decision
can fail.

## What v0.1 does not yet teach

v0.1 does not publish new benchmark scores, assert that any split is leakage
free by default, or certify reproducibility from a repository link alone.
